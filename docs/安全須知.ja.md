## GitHub に絶対アップロードしてはいけないもの

以下はすべて `.gitignore` に登録済みです。**コミット前にもう一度確認してください。**

| 分類 | 項目 |
|---|---|
| 資格情報 | API キー、管理者パスワード、セッションシークレット、`.env`、`*.pem`、`*.key`、`*.pfx` |
| 設定 | 実運用の `config/config.json`（リポジトリに入れるのは `config.example.json` のみ） |
| データ | `data/`、`*.db`、`users.db`、`usage.db`、リクエストログ、人事データ |
| モデル | `models/`、`*.gguf`、`*.safetensors`、モデルのライセンス証書 |
| 社内ネットワーク | 内部 IP 一覧、NAS／ルーターのアドレス、`lan-hosts.txt` |
| バックアップ | `backups/`、`exports/`、`*.bak` |

誤ってステージしていないか確認：

```bash
git status --porcelain
git check-ignore -v config/config.json data/agibar.db
```

機密が**すでに**コミットされてしまった場合、`.gitignore` を直すだけでは不十分です ——
履歴には残っています。当該資格情報をローテーション（API キーの再発行、管理者パスワードの変更、
`data/session.secret` の再生成）し、必要であれば `git filter-repo` で履歴を書き換えてください。

## 管理インターフェースのアクセス隔離

**既定では AI ホスト本体からのみ管理コンソールを開けます。** LAN の利用者に見えるのは
`/v1` と Web チャットだけです。

| パス | ローカル | LAN |
|---|---|---|
| `/`（ログインページ） | ✓ | 302 で `/chat.html` へ |
| `/app.html`（管理コンソール） | ✓ | **404** |
| `/api/*`（管理 API） | ✓ | **404** |
| `/assets/app.js`、`login.js` | ✓ | **404** |
| `/chat.html`（Web チャット） | ✓ | ✓ |
| `/v1/*`（API） | ✓ | ✓ |
| `/api/health`（監視用） | ✓ | ✓ |

### なぜ 403 ではなく 404 なのか

403 は相手に「ここには何かあるが、あなたは入れない」と伝えることになり、かえって攻撃する
価値のある標的を示してしまいます。404 なら、LAN から見て管理コンソールはそもそも存在しない
ように見えます。

### 「推測できない URL に移す」方式ではありません

管理コンソールをランダムなパスに置く方式は、誰かが一度 URL を見るか閲覧履歴を辿った時点で
破られます。ここで使っているのは**送信元アドレスによる判定**です。

- 根拠は TCP 接続の相手側アドレス（`req.socket.remoteAddress`）です。この値は偽装できません
  —— 3 ウェイハンドシェイクを完了させるには、パケットが実際にそのアドレスへ返せる必要が
  あるからです。
- **`X-Forwarded-For` は決して使いません。** あれはリクエストヘッダーで誰でも自分で書けます。
  アクセス制御に使うのは、制御していないのと同じです。`server.trustProxy` が有効でも同様で、
  あの設定が影響するのは「ログにどの IP を書くか」だけであり、認可判定には関与しません。

### 設定

```json
{
  "security": {
    "adminAccess": "loopback",
    "adminAllowedCidrs": []
  }
}
```

- `loopback`（既定）—— AI ホスト本体のみ
- `lan` —— 同一セグメントからアクセス可（**必要だと確信できる場合のみ変更**）
- `adminAllowedCidrs` —— 特定の送信元を追加で許可。例：管理者自身の PC
  `["192.168.1.50/32"]`

### 副作用

負荷テストと互換性検証のスクリプトはテスト用の利用者を作成するために管理 API を必要とするため、
**AI ホスト上で実行する**か、実行マシンの IP を `adminAllowedCidrs` に追加してください。
互換性プローブは `--key` で既存の API キーを直接指定することもでき、その経路には管理権限は
不要です。

### リバースプロキシ経由で外部公開する場合

プロキシを挟むとすべてのリクエストの送信元アドレスがプロキシ自身（通常はループバック）に
なるため、**管理コンソールは全員に開放されたのと同じ**になります。この構成では
`/app.html` と `/api/`（`/api/health` を除く）をプロキシ層で自分で遮断する必要があり、
ここの設定だけに頼ることはできません。

## 既知の制限

以下は V1 が明確に**カバーしない**範囲です。デプロイ時に各自で補ってください。

- **TLS なし。** サービスは HTTP で動きます。API キーは LAN 上を平文で流れます。外部公開や
  信頼できないセグメントをまたぐ場合は、Nginx / Caddy のリバースプロキシ背後に置いて HTTPS を
  有効にし、`security.forceHttpsCookies` を `true` にしてください。
- **Web チャット独自の認証はありません。** API キーをブラウザーの localStorage に保存します。
  共用 PC では、使い終わったら消すよう利用者に周知してください。
- **管理コンソールに二要素認証はありません。** V1 はパスワード＋ログインレート制限のみです。
- **トークン推定は厳密なトークナイザーではありません。** 上流が `usage` を返す場合はその値を
  優先し、無い場合はヒューリスティック（CJK 文字は約 1 トークン、それ以外は約 4 文字で
  1 トークン）で推定します。クォータ判定に誤差が出ることがあるため、ハードリミットには
  余裕を持たせてください。
- **同時実行数と RPM のカウントはメモリ上にあります。** サービス再起動でゼロに戻ります。
  トークンクォータはデータベースにあるため影響を受けません。
- **ブルートフォース対策のロックアウトはありません。** IP ごとの毎分ログイン回数制限のみで、
  アカウントロックはありません。

## デプロイ前チェックリスト

- [ ] 初期管理者パスワードを変更済み（`agibar-admin` のままにしない）
- [ ] `config/config.json` が git の追跡外（`git check-ignore` で確認）
- [ ] `data/session.secret` が自動生成され、リポジトリに入っていない
- [ ] 外部クラウドモデル（DeepSeek など）を有効にすべきか判断済み。既定は無効
- [ ] 外部モデルの資格情報は環境変数に置き、`config.json` には書いていない
- [ ] `server.host` を用途に応じて設定（`0.0.0.0` で LAN 公開／`127.0.0.1` でローカルのみ）
- [ ] ファイアウォール規則が承認され、ポートと実行ファイルのパスを EDR に届出済み
- [ ] `logging.logPrompts` が `false`（既定ではハッシュのみ記録）
- [ ] `logging.retentionDays` を保持ポリシーに合わせて設定（ログファイルとデータベース記録の
      両方が対象。0 で永久保持）
- [ ] バックアップが有効で、`data/backups/` にファイルが生成されている
- [ ] 利用者ごとに妥当なトークンクォータと時間帯を設定済み
- [ ] `security.adminAccess` が `loopback`（開放が必要だと確信できる場合を除く）
- [ ] LAN 上の別マシンから `/app.html` が 404 を返すことを実測済み
- [ ] `npm test` を実行し、169 項目すべて成功
- [ ] 負荷テストを実行し（[tests/load/README.ja.md](../tests/load/README.ja.md) 参照）、
      受け入れ判定がすべて通過

## セキュリティ問題の報告

`security` ラベルを付けて Issue を作成してください。未修正かつ悪用可能な問題の場合は、
GitHub の **Private vulnerability reporting**（Security タブ）で非公開に報告し、
修正後に公開してください。

いずれの方法でも、実際の API キー・パスワード・内部ネットワークアドレスは**絶対に**
含めないでください。再現手順にはプレースホルダーを使ってください。
