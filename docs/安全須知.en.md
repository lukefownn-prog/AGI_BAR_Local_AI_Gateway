## Never commit these to GitHub

Everything below is already in `.gitignore`. **Check once more before you commit.**

| Category | Items |
|---|---|
| Credentials | API keys, admin password, session secret, `.env`, `*.pem`, `*.key`, `*.pfx` |
| Config | The real `config/config.json` (only `config.example.json` belongs in the repo) |
| Data | `data/`, `*.db`, `users.db`, `usage.db`, request logs, personnel data |
| Models | `models/`, `*.gguf`, `*.safetensors`, model licence certificates |
| Internal network | Internal IP lists, NAS/router addresses, `lan-hosts.txt` |
| Backups | `backups/`, `exports/`, `*.bak` |

Check for accidental staging:

```bash
git status --porcelain
git check-ignore -v config/config.json data/agibar.db
```

If a secret has **already** been committed, editing `.gitignore` is not enough — the history still
contains it. You must rotate that credential (reissue the API key, change the admin password,
regenerate `data/session.secret`) and, if necessary, rewrite history with `git filter-repo`.

## Admin interface access isolation

**By default only the AI host itself can open the admin console.** LAN users see only `/v1` and
the web chat.

| Path | Local | LAN |
|---|---|---|
| `/` (sign-in page) | ✓ | 302 redirect to `/chat.html` |
| `/app.html` (console) | ✓ | **404** |
| `/api/*` (admin API) | ✓ | **404** |
| `/assets/app.js`, `login.js` | ✓ | **404** |
| `/chat.html` (web chat) | ✓ | ✓ |
| `/v1/*` (API) | ✓ | ✓ |
| `/api/health` (monitoring) | ✓ | ✓ |

### Why 404 rather than 403

A 403 tells the caller "there is something here, you just cannot have it" — which points at a
target worth attacking. A 404 makes the console look, from the LAN, as though it does not exist.

### This is not "move it to a URL nobody can guess"

Relocating the console to a random path fails the moment someone sees the URL once or finds it in
browser history. What is used here is **source-address checking**:

- The basis is the peer address of the TCP connection (`req.socket.remoteAddress`). That value
  cannot be forged — for the three-way handshake to complete, packets must genuinely reach that
  address.
- **`X-Forwarded-For` is never used.** It is a request header that anyone can set; using it for
  access control is the same as having no control. This holds even with `server.trustProxy`
  enabled — that setting only affects which IP is written to the logs, not the authorisation
  decision.

### Configuration

```json
{
  "security": {
    "adminAccess": "loopback",
    "adminAllowedCidrs": []
  }
}
```

- `loopback` (default) — the AI host only
- `lan` — anyone on the same segment (**change this only when you are sure you need it**)
- `adminAllowedCidrs` — additionally allow specific sources, e.g. the administrator's own machine:
  `["192.168.1.50/32"]`

### Side effects

The load-test and compatibility scripts need the admin API to create test users, so they **must be
run on the AI host** — or you must add the running machine's IP to `adminAllowedCidrs`. The
compatibility probe can also be pointed at an existing API key with `--key`; that path needs no
admin privileges.

### Exposing it through a reverse proxy

A proxy makes every request appear to come from the proxy itself (usually a loopback address),
which means **the console becomes open to everyone**. Such a deployment must block `/app.html` and
`/api/` (except `/api/health`) at the proxy layer; the settings here are not enough on their own.

## Known limitations

The following are explicitly **out of scope** for V1. Cover them yourself when deploying:

- **No TLS.** The service speaks HTTP. API keys travel the LAN in plaintext. Before exposing it
  externally or across untrusted segments, put it behind an Nginx / Caddy reverse proxy with
  HTTPS and set `security.forceHttpsCookies` to `true`.
- **No separate authentication for the web chat.** It stores the API key in the browser's
  localStorage. On shared computers, remind people to clear it when they finish.
- **No two-factor authentication for the console.** V1 has password plus login rate limiting only.
- **Token estimation is not an exact tokenizer.** When upstream reports `usage`, that value is
  used; otherwise a heuristic applies (roughly 1 token per CJK character, roughly 1 token per 4
  characters otherwise). Quota decisions can therefore be slightly off — leave headroom on hard
  limits.
- **Concurrency and RPM counters live in memory.** They reset when the service restarts. Token
  quotas live in the database and are unaffected.
- **No brute-force lockout.** There is only a per-IP, per-minute login rate limit; accounts are
  never locked.

## Pre-deployment checklist

- [ ] Initial admin password changed (not `agibar-admin`)
- [ ] `config/config.json` is not tracked by git (confirm with `git check-ignore`)
- [ ] `data/session.secret` was generated automatically and is not in the repository
- [ ] Decided whether external cloud models (DeepSeek etc.) should be enabled; disabled by default
- [ ] External model credentials are in environment variables, not in `config.json`
- [ ] `server.host` set as needed (`0.0.0.0` for LAN, `127.0.0.1` for local only)
- [ ] Firewall rule approved; port and executable path registered with EDR
- [ ] `logging.logPrompts` is `false` (only hashes are logged by default)
- [ ] `logging.retentionDays` set to match your retention policy (it covers both log files and
      database records; 0 means keep forever)
- [ ] Backups enabled and files are appearing in `data/backups/`
- [ ] Sensible token quotas and time windows configured for every user
- [ ] `security.adminAccess` is `loopback` (unless you are certain you need it open)
- [ ] Verified from another machine on the LAN that `/app.html` returns 404
- [ ] `npm test` run, all 169 passing
- [ ] Load test run (see [tests/load/README.en.md](../tests/load/README.en.md)) with all acceptance
      criteria passing

## Reporting security issues

Open an issue with the `security` label. If the issue is unfixed and exploitable, use GitHub's
**Private vulnerability reporting** (Security tab) instead, and disclose it publicly once a fix is
available.

Either way, **never** include real API keys, passwords or internal network addresses — use
placeholders in reproduction steps.
