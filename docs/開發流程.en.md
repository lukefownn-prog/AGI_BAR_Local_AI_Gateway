## Repository settings

**This repository is public, released under the MIT licence.**

Code, issues, versions, releases and documentation are managed on GitHub. Model files, API keys,
usage logs, databases and organisation-internal configuration **must not** be uploaded (see
[安全須知.md](安全須知.md) / [Security notes](安全須知.en.md)). A public repository makes that
rule more important, not less — anything committed by mistake is visible to everyone, and editing
`.gitignore` afterwards does not remove it from history.

## Development flow

```
Confirm requirement → open a GitHub issue → create a feature branch
   → develop with Codex / Claude Code / Cursor → test locally
   → commit → push → pull request → code review → automated tests
   → merge to main → tag the version → GitHub release
   → build the portable ZIP → deploy AGI BAR
```

## Branch rules

| Branch | Purpose |
|---|---|
| `main` | Stable, releasable |
| `develop` | Integration for the next version (optional) |
| `feature/xxx` | New features, e.g. `feature/api-key-quota` |
| `fix/xxx` | Bug fixes |
| `docs/xxx` | Documentation and specification updates |

```bash
git switch -c feature/embeddings-endpoint
# …develop…
npm test
git commit -m "feat(api): add the /v1/embeddings endpoint

Closes #12"
git push -u origin feature/embeddings-endpoint
gh pr create --fill
```

## Commit messages

Conventional Commits:

```
feat(scope): new feature
fix(scope): bug fix
docs(scope): documentation
test(scope): tests
refactor(scope): refactoring
chore(scope): chores
```

Common scopes: `api`, `admin`, `queue`, `router`, `quota`, `ui`, `scripts`.

## AI development tools and GitHub (design document 15.4)

Codex, Claude Code and Cursor all work from the **same git repository**.

**Rules:**

1. Before changing code, the AI reads the issue and the current branch
2. **Only touch files within that issue's scope**
3. Run `npm test` when finished; commit only when everything passes
4. **Avoid several AIs editing `main` directly** — always go through a feature branch + PR

**Suggested division of labour:**

| Tool | Role |
|---|---|
| Codex | Implementation, fixes, tests, git operations |
| Claude Code | Large features, architectural refactoring, code review |
| Cursor | Interactive hand-editing and quick checks |
| DeepSeek | A local/external code model or second opinion, still through the same git flow |

## CI (design document 16.2)

Every pull request automatically runs:

1. **Syntax check** — `node --check` across every `.mjs`
2. **Unit tests** — queue, quotas, time-based access, CIDR matching
3. **API tests** — the end-to-end pipeline (including failover with mock models)
4. **Security scan** — checks for secrets that slipped into the repository, and `.gitignore`
   coverage
5. **Portable structure check** — confirms required files are present and there are no npm
   dependencies

A release may only be created after `main` passes. **Sensitive settings needed for production are
never placed in an Actions artifact.**

## Release process (design document 16.3)

```bash
# 1. Confirm main is stable
git switch main && git pull && npm test

# 2. Update CHANGELOG.md and the version in package.json

# 3. Tag it
git tag -a v1.2.1 -m "v1.2.1"
git push origin v1.2.1

# 4. Build the portable ZIP (the SHA-256 is computed at the same time)
npm run build:portable

# 5. Create the release and upload
gh release create v1.2.1 \
  dist/AGI-BAR-v1.2.1-win64.zip \
  dist/AGI-BAR-v1.2.1-win64.zip.sha256 \
  --title "v1.2.1" --notes-file docs/release-notes/v1.2.1.md
```

The administrator downloads the ZIP → verifies the SHA-256 → unzips → **keeps the existing `data/`
and `config/`** → starts the service → runs a health check.

## How the portable ZIP relates to GitHub (design document 16.4)

- The **GitHub repository** holds the code
- A **GitHub release** provides the deployable ZIP
- **Large GGUF models never enter the git repository**; the administrator places them into
  `models/` after the first deployment

## Version numbers

Semantic Versioning:

- **MAJOR** — incompatible API or database schema changes (a migration script is required)
- **MINOR** — backwards-compatible new features
- **PATCH** — backwards-compatible fixes

When the database schema changes, say so explicitly in `CHANGELOG.md` and add that version's
migration steps to `docs/部署.md`.
