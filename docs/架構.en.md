## Request pipeline

```
User / AI dev tool / App
        │  Authorization: Bearer agi-bar-xxxxxxxx
        ▼
┌──────────────────────────────────────────────────────────┐
│ AGI BAR Web Gateway  (server/index.mjs)                  │
├──────────────────────────────────────────────────────────┤
│ 1. API auth       authenticateApiKey()  SHA-256 compare  │
│ 2. Time access    checkTimeWindow()     date/weekday/slot│
│ 3. Token quota    preflight()           4 tiers          │
│ 4. Concurrency    acquireSlot()         per key          │
│ 5. Priority queue queue.acquire()       P0-P3 + no starve│
│ 6. Model router   callWithFailover()    rank 1→2→3→4     │
└──────────────────────────────────────────────────────────┘
        ▼
Local model pool: local-primary → local-secondary → local-small
```

A failure at any stage is returned in the OpenAI error format so clients can show a readable
message. Whether the request succeeds or fails, the `finally` block always releases the queue slot
and the concurrency counter, and writes to `usage_logs` and `request_logs`.

## AGI BAR does not run inference

This is the most common misconception, so it belongs up front.

AGI BAR is a **gateway**: authentication, quotas, time-based access, queueing, routing, logging.
The things that actually load models and produce tokens are Ollama / LM Studio / llama.cpp /
vLLM — AGI BAR simply forwards requests to them over HTTP.

Consequently:

- **No code reads the project's `models/` folder.** Dropping GGUF files in there does nothing.
- Adding a model = install it into an inference service (`ollama pull …`) + register its endpoint
  in the admin console.
- Load time, VRAM usage and token throughput are all determined by the inference service.
  AGI BAR only observes and records them.

`models/` remains in the directory structure to match §11 of the design document, for deployments
that bundle their own llama.cpp.

## Module responsibilities

| File | Responsibility |
|---|---|
| `core/paths.mjs` | Single source of truth for all paths; supports `AGIBAR_DATA_DIR` isolation |
| `core/config.mjs` | Config loading and merging; external credentials come only from env vars |
| `core/db.mjs` | SQLite access (`node:sqlite`), transactions, audit |
| `core/crypto.mjs` | scrypt passwords, API key generation and hashing, HMAC signing |
| `core/http.mjs` | Mini router, JSON parsing, cookies, SSE |
| `services/users.mjs` | User CRUD, initial administrator |
| `services/apikeys.mjs` | Key lifecycle, limit fields, Bearer authentication |
| `services/quota.mjs` | Time access, four-tier quotas, RPM, concurrency, token estimation |
| `services/models.mjs` | Model registry, health checks, statistics |
| `services/routes.mjs` | Per-user model routing chain |
| `services/queue.mjs` | Priority queue + anti-starvation |
| `services/gateway.mjs` | Wires the whole pipeline together, failover, logging |
| `services/backup.mjs` | Consistent backups and retention policy |
| `services/retention.mjs` | Purging of expired records (usage / request / audit) |
| `services/anthropic-compat.mjs` | Anthropic ↔ OpenAI two-way translation (pure functions) |

Load-testing tools live in `tests/load/`: `loadtest.mjs` (the driver), `stats.mjs` (statistics and
acceptance criteria, pure functions) and `mock-farm.mjs` (a fake model farm so CI can keep
verifying the script in a GPU-less environment).

## Failover decisions

`isUsable()` treats a model as unavailable when (design document §7):

- `enabled = 0` — disabled by the administrator
- `health_state = 'offline'` and consecutive failures ≥ `unhealthyAfterFailures`
- `queue_depth ≥ queueTooLongThreshold` — the queue is too long

Additional handling when calling upstream:

- HTTP 5xx, connection failure, timeout → move to the next rank
- HTTP 429 / 408 / 409 / 425 → move to the next rank (this host may simply be busy)
- Any other 4xx → **do not switch**; report it directly. The request itself is malformed, and
  another model will not fix it.

## Anti-starvation

Effective weight = base weight − min(maxBoost, ⌊wait time / boostEveryMs⌋). Lower runs sooner.

With the defaults `boostEveryMs = 10000` and `maxBoost = 3`, a P3 guest request that has waited
30 seconds drops to an effective weight of 0 — the same tier as a P0 administrator. Equal weights
are served first-in, first-out.

## Tables

| Table | Purpose |
|---|---|
| `users` | Users and roles |
| `api_keys` | Key identifier, hash, status |
| `api_key_limits` | Token / time / RPM / concurrency limits |
| `models` | Models, endpoints, status, capabilities, health observations |
| `model_routes` | Per-user model priority order |
| `usage_logs` | Input/output/total tokens and per-model usage |
| `request_logs` | Time, wait, inference, errors |
| `audit_logs` | Audit trail of administrative actions |
| `admin_sessions` | Administrator sessions |
| `system_settings` | Global settings and security policy |

V1 uses SQLite (WAL mode). Multi-administrator or multi-node setups would move to PostgreSQL
later — every query is written in standard SQL, so migration mainly means adjusting functions
like `datetime('now')` and `strftime`.

## Why zero dependencies

The goal of the portable ZIP is "unzip and run". Any npm dependency brings three problems: it
requires `npm install`, it may need native module compilation, and it carries supply-chain risk.

Node's built-in `node:sqlite` removes the need for `better-sqlite3` (it landed in Node 22.5 behind
the `--experimental-sqlite` flag and became flag-free in 23.4, which is why this project requires
**Node 24 LTS or newer**); `node:http` and `node:crypto` are enough for a gateway of this size.

The cost is roughly 200 lines of hand-written mini-router and SSE handling. What that buys is zero
installation and zero supply-chain risk.
