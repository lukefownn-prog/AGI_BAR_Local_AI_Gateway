## リポジトリの設定

**本リポジトリは Public であり、MIT ライセンスで公開しています。**

コード、Issue、バージョン、リリース、ドキュメントは GitHub で管理します。モデルファイル、
API キー、利用ログ、データベース、組織内部の設定は**アップロードしないでください**
（[安全須知.md](安全須知.md) ／ [セキュリティ注意事項](安全須知.ja.md) 参照）。
公開リポジトリではこのルールの重要度がさらに上がります —— 誤ってコミットしたものは誰にでも
見え、後から `.gitignore` を直しても履歴からは消えません。

## 開発フロー

```
要件確認 → GitHub Issue 作成 → 機能ブランチ作成
   → Codex / Claude Code / Cursor で開発 → ローカルテスト
   → コミット → プッシュ → Pull Request → コードレビュー → 自動テスト
   → main へマージ → バージョンタグ作成 → GitHub Release
   → ポータブル ZIP を生成 → AGI BAR をデプロイ
```

## ブランチ規則

| ブランチ | 用途 |
|---|---|
| `main` | 安定版・リリース可能 |
| `develop` | 次バージョンの機能統合（任意） |
| `feature/xxx` | 新機能。例：`feature/api-key-quota` |
| `fix/xxx` | バグ修正 |
| `docs/xxx` | ドキュメントと仕様の更新 |

```bash
git switch -c feature/embeddings-endpoint
# …開発…
npm test
git commit -m "feat(api): /v1/embeddings エンドポイントを追加

Closes #12"
git push -u origin feature/embeddings-endpoint
gh pr create --fill
```

## コミットメッセージ

Conventional Commits を採用：

```
feat(scope): 新機能
fix(scope): 修正
docs(scope): ドキュメント
test(scope): テスト
refactor(scope): リファクタリング
chore(scope): 雑務
```

よく使う scope：`api`、`admin`、`queue`、`router`、`quota`、`ui`、`scripts`。

## AI 開発ツールと GitHub（企画書 15.4）

Codex、Claude Code、Cursor はいずれも**同一の Git リポジトリ**を作業基盤とします。

**ルール：**

1. AI はコードを変更する前に Issue と現在のブランチを読む
2. **その Issue の範囲内のファイルだけを変更する**
3. 完了後に `npm test` を実行し、全項目通過してからコミットする
4. **複数の AI が `main` を直接編集するのは避ける** —— 必ず機能ブランチ + PR を経由

**推奨する役割分担：**

| ツール | 位置づけ |
|---|---|
| Codex | 実装、修正、テスト、Git 操作 |
| Claude Code | 大型機能、アーキテクチャのリファクタリング、コードレビュー |
| Cursor | 対話的な手作業の修正とクイックチェック |
| DeepSeek | ローカル／外部のコードモデル、あるいはセカンドオピニオン。同じ Git フローを通す |

## CI（企画書 16.2）

Pull Request ごとに自動実行されるもの：

1. **構文チェック** —— すべての `.mjs` に `node --check`
2. **ユニットテスト** —— キュー、クォータ、時間帯権限、CIDR 判定
3. **API テスト** —— エンドツーエンドのパイプライン（モックモデルによるフェイルオーバーを含む）
4. **セキュリティスキャン** —— 機密がリポジトリに紛れ込んでいないか、`.gitignore` の網羅性
5. **ポータブル構造チェック** —— 必要ファイルが揃っているか、npm 依存がないか

`main` が通過して初めて Release を作成できます。
**本番デプロイに必要な機密設定は Actions の Artifact に含めません。**

## リリース手順（企画書 16.3）

```bash
# 1. main が安定していることを確認
git switch main && git pull && npm test

# 2. CHANGELOG.md と package.json のバージョンを更新

# 3. タグを打つ
git tag -a v1.2.1 -m "v1.2.1"
git push origin v1.2.1

# 4. ポータブル ZIP をビルド（SHA-256 も同時に算出）
npm run build:portable

# 5. Release を作成してアップロード
gh release create v1.2.1 \
  dist/AGI-BAR-v1.2.1-win64.zip \
  dist/AGI-BAR-v1.2.1-win64.zip.sha256 \
  --title "v1.2.1" --notes-file docs/release-notes/v1.2.1.md
```

管理者は ZIP をダウンロード → SHA-256 を照合 → 展開 → **既存の `data/` と `config/` を維持**
→ 起動 → ヘルスチェック、の順に進めます。

## ポータブル ZIP と GitHub の関係（企画書 16.4）

- **GitHub リポジトリ**はコードを保持する
- **GitHub Release** がデプロイ可能な ZIP を提供する
- **大きな GGUF モデルは Git リポジトリに入れない**。管理者が初回デプロイ後に `models/` へ配置

## バージョン番号

セマンティックバージョニングを採用：

- **MAJOR** —— 非互換の API またはデータベース構造の変更（マイグレーションスクリプトが必要）
- **MINOR** —— 後方互換のある新機能
- **PATCH** —— 後方互換のある修正

データベース構造に変更がある場合は `CHANGELOG.md` に明記し、
`docs/部署.md` にそのバージョンの移行手順を追記してください。
