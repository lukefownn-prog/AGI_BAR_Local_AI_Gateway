# デプロイガイド

[繁體中文](部署.md) ｜ [English](部署.en.md) ｜ **日本語**

> 企画書の第 11、16.3、16.5 節に対応します。

## 初回デプロイ

1. GitHub Release から `AGI-BAR-v1.2.0-win64.zip` をダウンロード
2. **SHA-256 を照合**（Release ページに記載）：
   ```powershell
   Get-FileHash .\AGI-BAR-v1.2.0-win64.zip -Algorithm SHA256
   ```
3. 固定パス（例：`D:\AGI-BAR\`）へ展開。`Program Files` は書き込み権限の問題が出るため避ける
4. ホストに Node.js 24+ が無い場合は `runtime\` に `node.exe` を配置
5. **`啟動 AGI BAR.cmd`** をダブルクリック
6. ブラウザーが自動で `http://localhost:8787` を開く
7. コンソールに表示された初期アカウントでログインし、**ただちに「設定」ページで
   パスワードを変更**
8. `config\config.json` の `models.catalog` をローカルモデルに向けて編集し、再起動
9. 「人員」ページで利用者を作成。API キーは自動で発行されます

## ローカルモデルの追加

> **先に一点はっきりさせておきます：AGI BAR は推論を実行せず、モデルファイルも保存しません。**
>
> これは**ゲートウェイ**であり、認証・クォータ・キューイング・ルーティングを担当します。
> 実際にモデルを動かすのは Ollama / LM Studio / llama.cpp / vLLM です。
>
> したがって GGUF ファイルをプロジェクトの `models/` フォルダーに置いても
> **まったく効果はありません** —— コードのどこからも読まれません。あのフォルダーが
> 意味を持つのは、llama.cpp を自分で `runtime/` に配置した場合だけです
> （llama.cpp が GGUF を読むため）。
>
> Ollama は独自の保存場所を持ちます（Windows の既定は `%USERPROFILE%\.ollama\models`。
> 内容アドレス指定の blob で保存され、そのまま持ち運べる GGUF ファイルではありません）。
> `OLLAMA_MODELS` 環境変数で制御します。

### モデルを 1 つ追加するには

**手順 1：推論サービスに導入する**

```bash
ollama pull qwen2.5:7b
```

**手順 2：AGI BAR に登録する**

管理コンソールの「AI モデル」ページで **＋ モデル追加** を押します。

1. よく使うサービスのボタンでエンドポイントを入力（Ollama は
   `http://localhost:11434/v1`）、または自分で入力
2. **探索** を押して、そのサービスに導入済みのモデルを一覧表示
3. 表示名、コンテキスト長、VRAM を調整して **追加** を押す

追加すると**即座に反映され、再起動は不要**です。既定ルートの最後尾に自動配置されます ——
ルートに入っていないモデルは、存在していてもどのリクエストからも選ばれません。

設定は `config/config.json` の `models.catalog` に書き戻され、そこが唯一の設定元であることは
変わりません（データベースにだけ書くと、次回起動時に設定ファイルで上書きされます）。

よく使うエンドポイント：

| サービス | エンドポイント |
|---|---|
| Ollama | `http://localhost:11434/v1` |
| LM Studio | `http://localhost:1234/v1` |
| llama.cpp server | `http://localhost:8080/v1` |
| vLLM | `http://localhost:8000/v1` |

> **Ollama の初回呼び出しは非常に遅くなります。** モデルを VRAM に読み込む必要があるためで、
> 実測では最初のメッセージに約 60 秒かかり、その後は通常の速度に戻りました。これは
> `queue.queueTimeoutMs` の既定値 120 秒より短いためタイムアウトはしませんが、その値を
> 下げていたり、クライアント側のタイムアウトが短い場合、初回呼び出しは故障したように
> 見えます。ホストで `ollama run <モデル>` を一度実行して暖機しておくとよいでしょう。

コンテキスト長と VRAM はダッシュボード表示とクォータ超過時のモデル選択にのみ影響するため、
おおよその値で構いません。

## ファイアウォールと EDR

サービスは既定で `0.0.0.0:8787` を待ち受け、LAN 内の利用者が接続できるようにしています。

- **Windows ファイアウォール**：初回起動時にダイアログが出るので「プライベートネットワーク」を許可
- 手動でルールを追加する場合：
  ```powershell
  New-NetFirewallRule -DisplayName "AGI BAR" -Direction Inbound -LocalPort 8787 -Protocol TCP -Action Allow -Profile Private
  ```
- **企業の EDR** はポリシーによってバッチスクリプトやネットワークを待ち受けるサービスを
  ブロックすることがあります。本番デプロイ前に**固定ポート**と**実行ファイルのパス**を
  申請・承認しておき、本番環境で黙って遮断される事態を避けてください（企画書 11）。

ローカルでのみ使う場合は `config.json` の `server.host` を `127.0.0.1` にします。

## コードとデータの分離

```
AGI-BAR/
├─ web/ server/ scripts/ runtime/   ← コード。更新時は丸ごと差し替え
├─ config/config.json               ← 設定。更新時は保持
├─ data/                            ← DB、ログ、バックアップ。更新時は保持
└─ models/                          ← GGUF モデル。更新時は保持
```

**更新用 ZIP で `config/`、`data/`、`models/` を上書きしてはいけません。**

## 更新手順（企画書 16.5）

1. まず手動バックアップを実行：管理コンソール →「設定」→「今すぐバックアップ」
2. サービスを停止（`關閉 AGI BAR.cmd`）
3. フォルダー全体を控えとしてコピー、少なくとも `config\` と `data\` はコピー
4. 新バージョンの ZIP を一時ディレクトリへ展開
5. 新しい `web\`、`server\`、`scripts\` で旧フォルダーの対応ディレクトリを上書き
6. `config\config.json`、`data\`、`models\` は**上書きしない**
7. 新しい `config\config.example.json` に追加項目が無いか比較し、必要なら `config.json` へ
   手動で追記（欠けている項目は例のデフォルトで自動補完されますが、新機能は調整が必要な
   場合があります）
8. サービスを起動して確認：
   - コンソールにエラーが無い
   - 「AI モデル」ページでモデルがオンライン
   - 「人員」ページの人数と API キー数が更新前と一致
   - 既存のキーで `/v1/models` を叩いて 200 が返る

## 旧バージョンへの復帰

1. サービスを停止
2. GitHub Release から前バージョンの ZIP をダウンロードし、コードディレクトリへ展開して上書き
3. 元の `data\` と `config\` を戻す（新バージョンが書き込んだ DB のカラムは旧バージョンから
   見れば余分なだけで SQLite は無視します。ただし逆は成立しません —— 旧バージョンに新しい
   テーブルが無いとエラーになるため、その場合は `data\backups\` の該当日付のバックアップを
   使ってください）
4. 起動してヘルスチェックを実行

## バックアップからの復元

バックアップは `data\backups\` に `agibar-<タイムスタンプ>.db` と同名の `.config.json` の
形式で保存されます。

復元手順：

1. サービスを停止
2. `data\agibar.db` をリネームして控えを残す
3. 復元したい `agibar-<タイムスタンプ>.db` を `data\agibar.db` としてコピー
4. 必要なら `agibar-<タイムスタンプ>.config.json` を `config\config.json` としてコピー
5. サービスを起動

> 復元すると、利用者・API キーのハッシュ・トークン統計がその時点まで巻き戻ります。
> その時点より後に発行したキーは無効になります。

## 起動・停止スクリプト

2 つの `.cmd` は**常に純 ASCII**で、メッセージは英語です。

理由：`cmd.exe` はバッチファイルを **コンソールのコードページ**（台湾では既定で CP950）で
解析し、UTF-8 では解析しません。UTF-8 で保存した中国語は Big5 として読まれて文字化けし、
さらに `chcp 65001` が途中でデコード方式を変えるため、cmd は解析位置を見失い、以降の行が
意味のない断片に切られます。画面には「'xxx' は内部コマンドまたは外部コマンド…」が並びます。
中国語のメッセージはすべて Node が出力します —— `chcp 65001` の後なら Node の UTF-8 は
正しく表示されます。`scripts/lint.mjs` が非 ASCII を含むバッチファイルを弾きます。

### 停止処理の仕組み

Windows には本当のシグナルがありません。`taskkill` が送るのは WM_CLOSE で、ウィンドウを
持たないコンソールプログラムには届かず、強制終了されるだけです —— データベースのクローズと
最後のログ書き込みが飛んでしまいます。

そこで `關閉 AGI BAR.cmd` は次のようにしています：

1. `data\shutdown.request` を作成する
2. サーバーは 1 秒ごとに確認し、見つけたら通常のシャットダウン手順に入る
   （ヘルスチェック停止、キューの排出、DB クローズ、ログの書き切り）
3. 最大 15 秒待ち、それでも終了しない場合のみ `taskkill /f`

正常時は `Service shut down cleanly.` と表示されます。
`Graceful shutdown timed out.` が出た場合はサービスが詰まっているので、
`data\logs\` を確認する価値があります。

## ポートが使用中の場合

起動後にブラウザーで AGI BAR ではない画面（JSON エラーなど）が出る場合、多くはポートの
衝突です。2 つのケースがあります。

**A. 完全に占有されている** —— AGI BAR がそもそも起動できず、コンソールに
「ポートが他のプログラムに使用されています」と、調査用コマンドおよび空いているポートの
提案が表示されます。

**B. 部分的な占有（Windows 特有で気づきにくい）** —— 別のサービスが IPv6 のワイルドカード
`::` にバインドし、AGI BAR は IPv4 の `0.0.0.0` にバインドしている状態です。Windows は両者の
共存を許しますが、**ブラウザーの `localhost` は IPv6 `::1` を優先して解決する**ため、接続が
相手に取られます。AGI BAR は動いているのに、画面は他人のもの、という状況です。

ケース B では起動時に次が表示されます：

```
┌──────────────────────────────────────────────────────────┐
│  ⚠  警告：このアドレスで応答しているのは本サービスではない │
└──────────────────────────────────────────────────────────┘
```

（起動後にサービスは自己確認を 1 回行います。自分のアドレスへリクエストを送り、
`X-AGI-BAR-Instance` ヘッダーが自プロセスのものか照合します。一致しなければ横取りされて
いるということです。）

占有しているプロセスの調べ方：

```powershell
Get-NetTCPConnection -LocalPort 8787 -State Listen |
  ForEach-Object { Get-Process -Id $_.OwningProcess | Select Id,ProcessName,Path }
```

対処はいずれか —— そのプログラムを終了する、または `config/config.json` の `server.port` を
変更する。**ポートを変えたら、すべてのクライアントの Base URL も併せて変更してください。**

## 監視

- コンソールへのリアルタイム出力。ファイルログは `data\logs\agibar-YYYY-MM-DD.log`（JSON Lines）
- ヘルスチェックエンドポイント：`GET /api/health`
  （ログイン不要。バージョン、稼働時間、キューの状態のみ返します）
- 管理ダッシュボードは 10 秒ごとに自動更新

ログの保持日数は `logging.retentionDays` で制御し、既定は 30 日です。ログファイルと
データベース内の利用・リクエスト・監査の記録の両方が対象で、期限を過ぎたものは自動削除されます。

## パフォーマンス調整

| 設定 | 既定 | 説明 |
|---|---|---|
| `queue.maxGlobalConcurrent` | 4 | 全体の同時推論数。**GPU の VRAM に合わせて調整**。高すぎると OOM |
| `queue.maxQueueLength` | 200 | キューの上限。超えたら即 503 |
| `queue.queueTimeoutMs` | 120000 | キューのタイムアウト |
| `models.healthCheckIntervalMs` | 15000 | ヘルスチェック間隔 |
| `models.queueTooLongThreshold` | 8 | 単一モデルのキューがこれを超えたら混雑と見なしフェイルオーバー |
| `server.requestTimeoutMs` | 300000 | 長い応答では大きくする。さもないと長文生成が途中で切れる |

50 名が同時にオンラインでも、実際の同時実行数はそれよりずっと少ないのが普通です。
まず `maxGlobalConcurrent = 4` から始め、ダッシュボードの「平均待ち時間」と VRAM 使用率を
見ながら上げてください。

感覚で調整しないこと —— 負荷テストスクリプトで計測します：

```bash
node tests/load/loadtest.mjs --url http://<AI ホストの IP>:8787 --admin-pass "…" --users 10 --duration 120
```

レポートには優先度ごとの待ち時間 p50/p95/max、キューのピーク深度、トークンの照合結果が
出力されます。詳細は **[tests/load/README.md](../tests/load/README.md)** を参照してください。

## 公開前の負荷受け入れテスト（M14）

利用者へ正式に開放する前に、最低でも次の 4 ラウンドを実施し結果を記録してください。

1. **ベースライン** —— 10 名 / 120 秒。通常負荷で異常がないことを確認
2. **ストリーミング** —— `--stream` を追加。実クライアントの多くはストリーミングで、
   レイテンシ特性が異なります
3. **Anthropic 経路** —— `--protocol anthropic` を追加し、Claude Code が通る経路を検証
4. **フルロード** —— 40〜50 名に近づけ、VRAM が OOM せず、キューが破綻しないことを確認

各ラウンド中は、管理コンソールの VRAM 使用率、AI ホストの `nvidia-smi`、
`data/logs/` にエラーが出ていないかを同時に監視してください。

**フェイルオーバーは手動検証が必要です：** 負荷テストの実行中に順位 1 のモデルサーバーを
手動で停止します。リクエストが成功し続け、管理コンソールでそのモデルがオフラインと表示され、
ログページにフェイルオーバーの印が現れることを確認してください。
