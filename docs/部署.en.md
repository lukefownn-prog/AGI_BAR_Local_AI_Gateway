# Deployment guide

> Corresponds to sections 11, 16.3 and 16.5 of the design document.

## First deployment

1. Download `AGI-BAR-v2.0.0-win64.zip` from the GitHub release
2. **Verify the SHA-256** (published on the release page):
   ```powershell
   Get-FileHash .\AGI-BAR-v2.0.0-win64.zip -Algorithm SHA256
   ```
3. Unzip to a fixed path such as `D:\AGI-BAR\` (avoid `Program Files` — write permissions become
   a problem)
4. If the host has no Node.js 24+, drop a `node.exe` into `runtime\`
5. Double-click **`啟動 AGI BAR.cmd`**
6. The browser opens `http://localhost:8787` automatically
7. Sign in with the initial credentials shown in the console, then **change the password on the
   Settings page immediately**
8. Edit `models.catalog` in `config\config.json` to point at your local model, then restart
9. Create users on the Users page; an API key is issued automatically for each

## Adding a local model

> **First, one thing to be clear about: AGI BAR does not run inference and does not store model
> files.**
>
> It is a **gateway** — authentication, quotas, queueing and routing. What actually runs the
> models is Ollama / LM Studio / llama.cpp / vLLM.
>
> Putting a GGUF file into the project's `models/` folder therefore **does nothing at all** —
> no code reads it. That folder only matters if you place llama.cpp into `runtime/` yourself
> (so llama.cpp can read the GGUF).
>
> Ollama has its own storage location (on Windows, `%USERPROFILE%\.ollama\models` by default),
> holding content-addressed blobs rather than portable GGUF files, controlled by the
> `OLLAMA_MODELS` environment variable.

### To add a model

**Step 1: install it into an inference service**

```bash
ollama pull qwen2.5:7b
```

**Step 2: register it with AGI BAR**

On the admin console's **AI Models** page, press **＋ Add model**:

1. Click a common-service button to fill in the endpoint (Ollama is
   `http://localhost:11434/v1`), or type your own
2. Press **Discover** to list the models installed in that service
3. Adjust the display name, context length and VRAM, then press **Add**

The model **takes effect immediately, with no restart**, and is placed at the end of the default
route — a model that is not in the route exists but will never be chosen by any request.

Settings are written back to `models.catalog` in `config/config.json`, which remains the single
source of truth (writing only to the database would be overwritten by the config file on the next
restart).

Common endpoints:

| Service | Endpoint |
|---|---|
| Ollama | `http://localhost:11434/v1` |
| LM Studio | `http://localhost:1234/v1` |
| llama.cpp server | `http://localhost:8080/v1` |
| vLLM | `http://localhost:8000/v1` |

> **The first call to Ollama is slow.** The model has to be loaded into VRAM first; in practice
> the first message took around 60 seconds before speed returned to normal. That is shorter than
> the 120-second default of `queue.queueTimeoutMs`, so it will not time out — but if you have
> lowered that value, or the client has a shorter timeout of its own, the first call will look
> broken. Run `ollama run <model>` once on the host to warm it up.

Context length and VRAM only affect the dashboard display and model selection when downgrading
over quota, so rough figures are fine.

## Firewall and EDR

The service listens on `0.0.0.0:8787` by default so LAN users can connect.

- **Windows firewall**: a prompt appears on first launch — allow "Private networks"
- To add the rule manually:
  ```powershell
  New-NetFirewallRule -DisplayName "AGI BAR" -Direction Inbound -LocalPort 8787 -Protocol TCP -Action Allow -Profile Private
  ```
- **Corporate EDR** may block batch scripts or network-listening services by policy. Before
  production deployment, submit the **fixed port** and **executable path** for approval so the
  service is not silently blocked in production (design document 11).

For local-only use, set `server.host` in `config.json` to `127.0.0.1`.

## Separating code from data

```
AGI-BAR/
├─ web/ server/ scripts/ runtime/   ← Code; replaced wholesale on update
├─ config/config.json               ← Config; preserved on update
├─ data/                            ← Database, logs, backups; preserved on update
└─ models/                          ← GGUF models; preserved on update
```

**An update ZIP must never overwrite `config/`, `data/` or `models/`.**

## Update procedure (design document 16.5)

1. Take a manual backup first: admin console → Settings → Back up now
2. Stop the service (`關閉 AGI BAR.cmd`)
3. Copy the whole folder aside, or at minimum copy `config\` and `data\`
4. Unzip the new version into a temporary directory
5. Overwrite the old `web\`, `server\` and `scripts\` with the new ones
6. **Do not** overwrite `config\config.json`, `data\` or `models\`
7. Compare the new `config\config.example.json` for added fields and merge them into
   `config.json` by hand (missing fields fall back to the example's defaults automatically, but
   new features may need tuning)
8. Start the service and confirm:
   - No errors in the console
   - Models show as online on the AI Models page
   - User count and API key count match what they were before the update
   - An existing key still gets a 200 from `/v1/models`

## Rolling back

1. Stop the service
2. Download the previous release ZIP and unzip it over the code directories
3. Put the original `data\` and `config\` back (database columns written by the newer version are
   simply redundant to the older one and SQLite ignores them — but not the reverse: if the older
   version is missing a new table it will error, in which case use the matching dated backup from
   `data\backups\`)
4. Start it and run a health check

## Restoring from backup

Backups live in `data\backups\` as `agibar-<timestamp>.db` plus a matching `.config.json`.

To restore:

1. Stop the service
2. Rename `data\agibar.db` to keep it aside
3. Copy the `agibar-<timestamp>.db` you want to restore to `data\agibar.db`
4. If needed, copy `agibar-<timestamp>.config.json` to `config\config.json`
5. Start the service

> Restoring rolls users, API key hashes and token statistics back to that point in time. Keys
> issued after that moment stop working.

## Start and stop scripts

Both `.cmd` files are **kept pure ASCII**, with English messages.

The reason: `cmd.exe` parses batch files using the **console code page** (CP950 by default in
Taiwan), not UTF-8. Chinese saved as UTF-8 is read as Big5 and turns into mojibake, and
`chcp 65001` changes the decoding mid-file, causing cmd to lose its parsing position so later
lines are chopped into meaningless fragments — the screen fills with "'xxx' is not recognised as
an internal or external command". Chinese messages are always emitted by Node instead, where
UTF-8 displays correctly after `chcp 65001`. `scripts/lint.mjs` rejects any batch file containing
non-ASCII bytes.

### How shutdown works

Windows has no real signals: `taskkill` sends WM_CLOSE, which a console program with no window
never receives, so it is simply terminated — skipping database close and the final log writes.

`關閉 AGI BAR.cmd` therefore:

1. Creates `data\shutdown.request`
2. The server checks once per second and, on seeing it, runs the normal shutdown sequence (stop
   health checks, drain the queue, close the database, finish writing logs)
3. Waits up to 15 seconds; only if it really has not exited does it `taskkill /f`

Normally you will see `Service shut down cleanly.` If you see
`Graceful shutdown timed out.`, the service was stuck and `data\logs\` is worth a look.

## Port already in use

If after starting you see something in the browser that is not AGI BAR (a JSON error, for
instance), it is usually a port conflict. There are two cases:

**A. Fully occupied** — AGI BAR cannot start at all; the console prints "the port is already in
use by another program" together with a lookup command and a suggested free port.

**B. Partially occupied (Windows-specific, harder to notice)** — another service is bound to the
IPv6 wildcard `::` while AGI BAR binds IPv4 `0.0.0.0`. Windows allows both to coexist, **but the
browser resolves `localhost` to IPv6 `::1` first**, so the connection goes to the other program.
AGI BAR is running, yet the page belongs to someone else.

Case B prints this at startup:

```
┌──────────────────────────────────────────────────────────┐
│  ⚠  Warning: something other than this service replied   │
└──────────────────────────────────────────────────────────┘
```

(After starting, the service checks itself once: it sends a request to its own address and
compares the `X-AGI-BAR-Instance` header against this process. A mismatch means it was
intercepted.)

To find the culprit:

```powershell
Get-NetTCPConnection -LocalPort 8787 -State Listen |
  ForEach-Object { Get-Process -Id $_.OwningProcess | Select Id,ProcessName,Path }
```

Then either close that program or change `server.port` in `config/config.json`.
**After changing the port, every client's base URL must change too.**

## Monitoring

- Live output in the console; file logs in `data\logs\agibar-YYYY-MM-DD.log` (JSON Lines)
- Health endpoint: `GET /api/health` (no login required; returns version, uptime and queue state)
- The admin dashboard refreshes every 10 seconds

Log retention is controlled by `logging.retentionDays`, 30 days by default. It covers both the log
files and the usage / request / audit records in the database; anything older is deleted
automatically.

## Performance tuning

| Setting | Default | Notes |
|---|---|---|
| `queue.maxGlobalConcurrent` | 4 | Global concurrent inferences. **Tune to your GPU VRAM** — too high causes OOM |
| `queue.maxQueueLength` | 200 | Queue cap; beyond this, 503 is returned immediately |
| `queue.queueTimeoutMs` | 120000 | Queue timeout |
| `models.healthCheckIntervalMs` | 15000 | Health check interval |
| `models.queueTooLongThreshold` | 8 | A model whose queue exceeds this is treated as congested and failed over |
| `server.requestTimeoutMs` | 300000 | Raise this for long responses, otherwise long generations get cut off |

Fifty people online rarely means fifty concurrent requests. Start at
`maxGlobalConcurrent = 4`, watch the dashboard's average wait and VRAM usage, then raise it.

Do not tune by feel — measure with the load-test script:

```bash
node tests/load/loadtest.mjs --url http://<AI-host-IP>:8787 --admin-pass "…" --users 10 --duration 120
```

The report gives p50/p95/max wait times per priority, peak queue depth and a token reconciliation.
Full details in **[tests/load/README.md](../tests/load/README.md)**.

## Pre-launch load acceptance (M14)

Before opening the service to users, run at least these four rounds and record the results:

1. **Baseline** — 10 users / 120 seconds, confirming normal load behaves
2. **Streaming** — add `--stream`; real clients mostly stream, and the latency profile differs
3. **Anthropic path** — add `--protocol anthropic` to verify the route Claude Code uses
4. **Full load** — push towards 40–50 users, confirming VRAM does not OOM and the queue stays
   under control

During each round, watch the dashboard's VRAM usage, `nvidia-smi` on the AI host, and whether any
errors appear in `data/logs/`.

**Failover needs manual verification:** while a load test is running, stop the rank-1 model server
by hand. You should see requests continue to succeed, the console show that model as offline, and
failover markers appear on the Logs page.
