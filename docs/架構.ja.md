## リクエストパイプライン

```
利用者 / AI 開発ツール / アプリ
        │  Authorization: Bearer agi-bar-xxxxxxxx
        ▼
┌────────────────────────────────────────────────────────────┐
│ AGI BAR Web Gateway  (server/index.mjs)                    │
├────────────────────────────────────────────────────────────┤
│ 1. API 認証        authenticateApiKey()  SHA-256 照合      │
│ 2. 時間帯権限      checkTimeWindow()     日付/曜日/時間帯  │
│ 3. トークン枠      preflight()           4 階層            │
│ 4. 同時実行制御    acquireSlot()         キー単位          │
│ 5. 優先度キュー    queue.acquire()       P0-P3 + 飢餓防止  │
│ 6. モデルルーター  callWithFailover()    順位 1→2→3→4      │
└────────────────────────────────────────────────────────────┘
        ▼
ローカルモデルプール：local-primary → local-secondary → local-small
```

いずれかの関門で失敗した場合も OpenAI 形式のエラーで返すため、クライアント側で読める
メッセージを表示できます。成功・失敗にかかわらず `finally` ブロックが必ずキューの枠と
同時実行カウントを解放し、`usage_logs` と `request_logs` に記録します。

## AGI BAR は推論を実行しません

最もよくある誤解なので、最初に書いておきます。

AGI BAR は**ゲートウェイ**です —— 認証、クォータ、時間帯権限、キューイング、ルーティング、
記録を担当します。実際にモデルを読み込んでトークンを生成するのは Ollama / LM Studio /
llama.cpp / vLLM であり、AGI BAR は HTTP でリクエストを転送しているだけです。

したがって：

- プロジェクトの `models/` フォルダーは**どのコードからも読まれません**。
  GGUF ファイルを置いても効果はありません。
- モデルの追加＝推論サービスへの導入（`ollama pull …`）＋管理コンソールでのエンドポイント登録。
- 読み込み時間、VRAM 使用量、トークン生成速度はすべて推論サービス側で決まります。
  AGI BAR はそれを観測して記録するだけです。

`models/` をディレクトリ構成に残しているのは企画書 §11 に対応するためで、
llama.cpp を自前で同梱する配置方式のために確保しています。

| `core/config.mjs` | 設定の読み込みと統合。外部の資格情報は環境変数からのみ取得 |
| `core/db.mjs` | SQLite アクセス（`node:sqlite`）、トランザクション、監査 |
| `core/crypto.mjs` | scrypt パスワード、API キーの生成とハッシュ、HMAC 署名 |
| `core/http.mjs` | ミニルーター、JSON 解析、Cookie、SSE |
| `services/users.mjs` | 利用者の CRUD、初期管理者 |
| `services/apikeys.mjs` | キーのライフサイクル、制限項目、Bearer 認証 |
| `services/quota.mjs` | 時間帯権限、4 階層クォータ、RPM、同時実行数、トークン推定 |
| `services/models.mjs` | モデル登録、ヘルスチェック、統計 |
| `services/routes.mjs` | 利用者ごとのモデルルーティングチェーン |
| `services/queue.mjs` | 優先度キュー + アンチスタベーション |
| `services/gateway.mjs` | パイプライン全体の結合、フェイルオーバー、記録 |
| `services/backup.mjs` | 整合性のあるバックアップと保持ポリシー |
| `services/retention.mjs` | 期限切れ記録の削除（usage / request / audit）|
| `services/anthropic-compat.mjs` | Anthropic ↔ OpenAI 双方向変換（純粋関数） |

継続的に検証できるようにするため）。

## フェイルオーバーの判定

`isUsable()` がモデルを利用不可と判断する条件（企画書 §7）：

- `enabled = 0` —— 管理者が無効化
- `health_state = 'offline'` かつ連続失敗回数 ≥ `unhealthyAfterFailures`
- `queue_depth ≥ queueTooLongThreshold` —— キューが長すぎる

上流呼び出し時の追加処理：

- HTTP 5xx、接続失敗、タイムアウト → 次の順位へ
- HTTP 429 / 408 / 409 / 425 → 次の順位へ（この 1 台が混んでいるだけの可能性）
- その他の 4xx → **切り替えない**。そのまま報告します。
  リクエスト自体に問題があるため、モデルを変えても解決しません。

## アンチスタベーション

実効ウェイト = 基礎ウェイト − min(maxBoost, ⌊待機時間 / boostEveryMs⌋)。小さいほど先に実行。

既定値 `boostEveryMs = 10000`、`maxBoost = 3` では、P3 ゲストのリクエストが 30 秒待つと
実効ウェイトが 0 になり、P0 管理者と同等になります。同ウェイトの場合は先入れ先出しです。

## テーブル

| テーブル | 用途 |
|---|---|
| `users` | 利用者と役割 |
| `api_keys` | キーの識別子、ハッシュ、状態 |
| `api_key_limits` | トークン / 時間 / RPM / 同時実行数の制限 |
| `models` | モデル、エンドポイント、状態、能力、ヘルス観測値 |
| `model_routes` | 利用者ごとのモデル優先順位 |
| `usage_logs` | Input/Output/合計トークンとモデル別使用量 |
| `request_logs` | 時刻、待機、推論、エラー |
| `audit_logs` | 管理操作の監査記録 |
| `admin_sessions` | 管理者セッション |
| `system_settings` | グローバル設定とセキュリティポリシー |

V1 は SQLite（WAL モード）を使用します。複数管理者や複数ノードが必要になった段階で
PostgreSQL へ移行する想定です —— クエリはすべて標準 SQL で書いてあるため、移行時に主に
調整するのは `datetime('now')` や `strftime` といった関数です。

## なぜ依存ゼロなのか

ポータブル ZIP の目標は「展開すればすぐ動く」ことです。npm 依存はどれも 3 つの問題を
持ち込みます —— `npm install` が必要になる、ネイティブモジュールのコンパイルが要る場合が
ある、サプライチェーンのリスクを負う。

Node 組み込みの `node:sqlite` により `better-sqlite3` が不要になりました（Node 22.5 で
`--experimental-sqlite` フラグ付きで導入され、23.4 からフラグ不要。本プロジェクトが
**Node 24 LTS 以上**を要求するのはこのためです）。`node:http` と `node:crypto` は、
この規模のゲートウェイには十分です。

代償は、ミニルーターと SSE 処理を約 200 行自前で書いたこと。引き換えに得たのは、
インストール不要とサプライチェーンリスクゼロです。
