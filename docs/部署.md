# 部署指南

> 對應規畫書第 11、16.3、16.5 節。

## 首次部署

1. 從 GitHub Release 下載 `AGI-BAR-v1.2.0-win64.zip`
2. **核對 SHA-256**（Release 頁面有附）：
   ```powershell
   Get-FileHash .\AGI-BAR-v1.2.0-win64.zip -Algorithm SHA256
   ```
3. 解壓到固定路徑，例如 `D:\AGI-BAR\`（避免放在 `Program Files`，會有寫入權限問題）
4. 若主機沒裝 Node.js 24+，把 `node.exe` 放進 `runtime\`
5. 雙擊 **`啟動 AGI BAR.cmd`**
6. 瀏覽器會自動開啟 `http://localhost:8787`
7. 以主控台顯示的初始帳密登入，**立即到「設定」頁修改密碼**
8. 編輯 `config\config.json` 的 `models.catalog` 指向你的本地模型，重新啟動
9. 到「人員」頁建立人員，系統會自動配發 API Key

## 防火牆與 EDR

服務預設監聽 `0.0.0.0:8787`，讓 LAN 內的人員可以連線。

- **Windows 防火牆**：首次啟動會跳出提示，請允許「私人網路」
- 手動新增規則：
  ```powershell
  New-NetFirewallRule -DisplayName "AGI BAR" -Direction Inbound -LocalPort 8787 -Protocol TCP -Action Allow -Profile Private
  ```
- **企業 EDR** 可能依政策攔截批次腳本或監聽網路的服務。
  正式部署前請請管理員把**固定 Port** 與**程式路徑**送交核准，
  避免服務在生產環境被靜默阻擋（規畫書 11）。

只想本機使用時，把 `config.json` 的 `server.host` 改成 `127.0.0.1`。

## 目錄與資料分離

```
AGI-BAR/
├─ web/ server/ scripts/ runtime/   ← 程式，更新時整包替換
├─ config/config.json               ← 設定，更新時保留
├─ data/                            ← 資料庫、紀錄、備份，更新時保留
└─ models/                          ← GGUF 模型，更新時保留
```

**更新 ZIP 不應覆蓋 `config/`、`data/`、`models/`。**

## 更新流程（規畫書 16.5）

1. 先執行一次手動備份：管理台 →「設定」→「立即備份」
2. 停止服務（`關閉 AGI BAR.cmd`）
3. 把整個資料夾複製一份留底，或至少複製 `config\` 與 `data\`
4. 解壓新版 ZIP 到暫存目錄
5. 用新版的 `web\`、`server\`、`scripts\` 覆蓋舊資料夾對應目錄
6. **不要**覆蓋 `config\config.json`、`data\`、`models\`
7. 比對新版 `config\config.example.json` 是否有新增欄位，手動補進 `config.json`
   （缺少的欄位會自動由範例補上預設值，但新功能可能需要調整）
8. 啟動服務，確認：
   - 主控台無錯誤
   - 管理台「AI 模型」頁模型狀態為線上
   - 「人員」頁人數與 API Key 數量與更新前一致
   - 用既有 Key 打一次 `/v1/models` 確認 200

## 回復舊版

1. 停止服務
2. 從 GitHub Release 下載前一版 ZIP，解壓覆蓋程式目錄
3. 把原本的 `data\` 與 `config\` 掛回去（新版寫入的資料庫欄位對舊版是多餘欄位，
   SQLite 會忽略，但反向不成立 —— 若舊版缺少新資料表會報錯，
   此時改用 `data\backups\` 中對應日期的備份）
4. 啟動並執行健康檢查

## 備份還原

備份檔在 `data\backups\`，格式為 `agibar-<時間戳>.db` 與同名的 `.config.json`。

還原步驟：

1. 停止服務
2. 把 `data\agibar.db` 改名留底
3. 把要還原的 `agibar-<時間戳>.db` 複製成 `data\agibar.db`
4. 需要時把 `agibar-<時間戳>.config.json` 複製成 `config\config.json`
5. 啟動服務

> 還原會一併回復人員、API Key 雜湊與 Token 統計到該時間點。
> 該時間點之後新發的 Key 會失效。

## 啟動與關閉腳本

兩支 `.cmd` **一律維持純 ASCII**，訊息是英文。

原因：`cmd.exe` 用**主控台編碼**（台灣預設 CP950）而非 UTF-8 解析批次檔。
存成 UTF-8 的中文會被當成 Big5 讀成亂碼，而 `chcp 65001` 又在中途改變解碼方式，
讓 cmd 失去解析位置，後面的行被切成無意義的碎片，畫面上會看到一堆
「'xxx' 不是內部或外部命令」。中文訊息一律由 Node 輸出 —— `chcp 65001` 之後
Node 的 UTF-8 就能正確顯示。`scripts/lint.mjs` 會擋下含非 ASCII 的批次檔。

### 關閉是怎麼運作的

Windows 沒有真正的訊號：`taskkill` 送的是 WM_CLOSE，沒有視窗的主控台程式
收不到，只會被強制終止 —— 那會跳過關閉資料庫與寫入最後的紀錄。

因此 `關閉 AGI BAR.cmd` 改為：

1. 建立 `data\shutdown.request`
2. 伺服器每秒檢查一次，看到就走正常關機流程（停健康檢查、排空佇列、
   關閉資料庫、寫完紀錄）
3. 等最多 15 秒；真的沒結束才 `taskkill /f`

正常情況下你會看到 `Service shut down cleanly.`。若看到
`Graceful shutdown timed out.`，代表服務卡住了，值得查 `data\logs\`。

## 監控

- 主控台即時輸出；檔案紀錄在 `data\logs\agibar-YYYY-MM-DD.log`（JSON Lines）
- 健康檢查端點：`GET /api/health`（不需登入，僅回傳版本、uptime 與佇列狀態）
- 管理台儀表板每 10 秒自動更新

紀錄保留天數由 `logging.retentionDays` 控制，預設 30 天，逾期自動刪除。

## 效能調整

| 設定 | 預設 | 說明 |
|---|---|---|
| `queue.maxGlobalConcurrent` | 4 | 全域同時推理數。**依 GPU VRAM 調整**，設太高會 OOM |
| `queue.maxQueueLength` | 200 | 佇列上限，超過直接回 503 |
| `queue.queueTimeoutMs` | 120000 | 排隊逾時 |
| `models.healthCheckIntervalMs` | 15000 | 健康檢查間隔 |
| `models.queueTooLongThreshold` | 8 | 單一模型 Queue 超過此值就視為壅塞並 Failover |
| `server.requestTimeoutMs` | 300000 | 長回應要調大，否則長文生成會被切斷 |

50 人同時在線但實際併發通常遠低於此。先從 `maxGlobalConcurrent = 4` 開始，
觀察儀表板的「平均等待」與 VRAM 使用率再往上調。

不要憑感覺調 —— 用壓測腳本量：

```bash
node tests/load/loadtest.mjs --url http://<AI主機IP>:8787 --admin-pass "…" --users 10 --duration 120
```

報表會給出各優先權的等待時間 p50/p95/max、佇列尖峰深度與 Token 對帳結果。
完整說明見 **[tests/load/README.md](../tests/load/README.md)**。

## 上線前的壓力驗收（M14）

正式開放給人員之前，至少跑完這四輪並記錄結果：

1. **基準** — 10 人 / 120 秒，確認常態負載無異常
2. **串流** — 加 `--stream`，真實客戶端多半用串流，延遲特性不同
3. **Anthropic 路徑** — 加 `--protocol anthropic`，驗證 Claude Code 走的那條線
4. **滿載** — 逼近 40-50 人，確認 VRAM 未 OOM、佇列未失控

每輪都要同步盯著管理台的 VRAM 使用率、AI 主機的 `nvidia-smi`，
以及 `data/logs/` 有無 error。

**Failover 需人工介入驗證：** 在壓測進行中手動停掉順位 1 的模型伺服器，
應觀察到請求持續成功、管理台顯示該模型離線、紀錄頁出現 Failover 標記。
